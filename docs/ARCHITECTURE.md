# Architecture

PAISAI is engineered as **regulated-grade financial software**. The architecture
is designed so that the founding principles are enforced by the *system*, not left
to the discretion of any single response.

---

## Technology stack

### Frontend

- **Next.js** + **React** + **TypeScript**
- **Tailwind CSS** + **shadcn/ui** for the component system
- **Framer Motion** for restrained, comprehension-serving motion

### Backend

- **FastAPI** (Python) for the API layer
- **PostgreSQL** as the system of record
- **Redis** for caching, rate limiting, and ephemeral state
- **Vector database** for retrieval over documents, filings, and knowledge
- **Celery** for asynchronous and scheduled work (reviews, simulations, ingestion)
- **WebSockets** for live market and portfolio updates

### Platform

- **Docker**, with a **Kubernetes-ready** architecture
- **CI/CD** with comprehensive automated testing
- **Observability:** structured logging, metrics, and distributed tracing

## Principle-enforcing layers

The following components exist specifically to make the data-integrity and
behaviour contracts structural rather than advisory.

### 1. Market Data Gateway

All market/reference data (prices, NAVs, fundamentals, macro, regulations) flows
through a single gateway backed by integrated providers. **The language model
never sources numbers from parametric memory.** The gateway attaches provenance
metadata (source, freshness) to every value and returns an explicit
"unavailable" state when a provider cannot be reached — never a guess.

### 2. Calculation Engine

Deterministic financial math (weights, CAGR, ratios, DCF, Monte Carlo) lives in a
tested engine, not in prose generated by the model. Any numeric the model wishes
to present must be produced or validated here, so that **Calculated** values are
reproducible and auditable.

### 3. Provenance & Validation Middleware

Between generation and the user sits a validation layer that:

- rejects or flags un-sourced numerics (No-Hallucination enforcement),
- ensures every value carries exactly one provenance category, and
- ensures material answers carry evidence, assumptions, risks, limitations, and a
  confidence level.

### 4. AI Orchestration Layer

Composes the system prompt (see [`prompts/SYSTEM_PROMPT.md`](prompts/SYSTEM_PROMPT.md)),
retrieves grounding context from the vector store and Market Data Gateway, and
routes model output through validation. Education and personalised guidance are
generated and labelled through distinct paths.

### 5. Decision Journal Service

Persists structured decision entries, schedules reviews (via Celery), runs
thesis-vs-reality comparisons, detects behavioural biases across history, and
computes the Personal Decision Quality Score. See
[`DECISION_JOURNAL.md`](DECISION_JOURNAL.md).

### 6. Audit Log

An append-only record of decisions, data sources consulted, and material AI
outputs — supporting the "auditable" property that trust depends on.

## Architectural principles

- **Modular architecture.** Modules (Dashboard, Expense Intelligence, etc.) are
  bounded and independently testable; they share the integrity/behaviour
  contracts, not internal state.
- **Comprehensive automated testing.** Financial correctness is covered by tests,
  including property/golden tests for the Calculation Engine and contract tests
  that assert un-sourced numerics are rejected.
- **Fail honest, not silent.** When data or a service is unavailable, the system
  surfaces that state to the user rather than degrading into a plausible guess.
- **Determinism where it matters.** Numbers come from deterministic engines;
  natural language explains them. The two are never confused.

## Data flow (typical query)

```
User query
   │
   ▼
AI Orchestration ──▶ Market Data Gateway ──▶ integrated providers (provenance-tagged)
   │                      │
   │                      └▶ "unavailable" state when a source is missing
   ▼
Calculation Engine (deterministic math on verified inputs)
   │
   ▼
Model generation (explanation, reasoning, teaching) — grounded, not inventing numbers
   │
   ▼
Provenance & Validation Middleware (reject un-sourced numerics; require the answer anatomy)
   │
   ▼
Audit Log  ──▶  User (values tagged by provenance; answer carries confidence + limitations)
```

Security and privacy requirements that constrain this architecture are documented
in [`SECURITY.md`](SECURITY.md).
